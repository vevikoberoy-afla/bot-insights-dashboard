VITTAIN AI — MULTI-BOT, MULTI-CHANNEL CLIENT ARCHITECTURE
==============================================================
Full feature spec: a client can create MULTIPLE bots, each bot has its
OWN channels (WhatsApp/Email/SMS/Web), OWN datasets, OWN chat history,
OWN tickets, OWN agents — plus a central admin system for YOU to track
usage and finances across every client and every bot.

==============================================================
PART 1 — THE CORE CONCEPT (read this first)
==============================================================

OLD MODEL (what you have now):
  1 Client = 1 Bot = 1 Context = 1 Website

NEW MODEL (what you're building):
  1 Client = MANY Bots
  Each Bot = its own context_id, its own knowledge base, its own
             channels, its own tickets, its own agents, its own analytics

WHY: A single business might want a "Sales Bot" on WhatsApp trained on
product catalog + pricing, and a completely separate "Support Bot" on
Email trained on troubleshooting docs. Different knowledge, different
tone, different channel — same client account.

EXAMPLE:
  Client: "Northwind Retail"
    Bot 1: "Sales Assistant" — connected to WhatsApp + Web Widget
           Dataset: product catalog, pricing sheet
    Bot 2: "Order Support" — connected to Email + SMS
           Dataset: order database (Google Sheets), shipping policy
    Bot 3: "HR Helpdesk" — connected to Web Widget only (internal use)
           Dataset: employee handbook PDF

Each bot is fully independent but rolls up into the same Client account
for billing and top-level reporting.

UPDATE — SHARED / SEPARATE DATASETS ACROSS BOTS
====================================================
This changes the relationship between Bots and Datasets from
1-to-1 to MANY-to-MANY.

------------------------------------
NEW CONCEPT
------------------------------------
A "Dataset" (a crawled website, an uploaded file set, a manual
knowledge base) is now its own independent object — NOT locked
to a single bot.

A Client can:
  - Crawl multiple different websites → each crawl creates a
    separate Dataset
  - Create multiple Bots → each Bot picks ONE OR MORE Datasets
    to pull knowledge from

EXAMPLE:
  Client: "Northwind Retail"
    Datasets:
      - "Main Website" (crawled northwindretail.com)
      - "Product Catalog PDF" (uploaded file)
      - "Support Docs Website" (crawled help.northwindretail.com)
      - "Order Database" (Google Sheets connection)

    Bots:
      - "Sales Bot" (WhatsApp) → uses: Main Website + Product Catalog PDF
      - "Support Bot" (Email)  → uses: Support Docs Website + Order Database
      - "General Bot" (Web Widget) → uses: ALL FOUR datasets combined

So two bots can share the exact same dataset, or each bot can have
its own completely separate dataset — client's choice, per bot.

------------------------------------
WHERE THIS LIVES IN THE UI
------------------------------------

NEW SIDEBAR-LEVEL SECTION (client-level, above Bots):
  Client Detail → Tab: "Datasets" (NEW TAB, sits next to "Bots" tab)
    - List of all datasets this client has created
    - "+ New Dataset" button → same creation flow as before
      (crawl URL / upload file / manual text / connect DB)
    - Each dataset card shows: name, type (Crawl/Upload/Manual/DB),
      size (chunk count), last updated, "used by N bots" tag

BOT CREATION WIZARD — updated Step 3:
  Old: "Build knowledge base" (crawl/upload/manual/db — created new)
  New: "Assign Datasets" — a multi-select list of the client's
       EXISTING datasets, with a "+ Create New Dataset" option
       inline if they want a fresh one just for this bot

BOT DETAIL PAGE — Tab 3 renamed:
  Old: "Datasets (Knowledge Base)" — owned the data directly
  New: "Datasets" — shows which datasets are LINKED to this bot,
       with:
         - Checklist of assigned datasets (toggle on/off)
         - "+ Link existing dataset" button
         - "+ Create new dataset for this bot" button
         - Each linked dataset shows a small "also used by: Sales
           Bot, General Bot" note if shared

------------------------------------
DATABASE SCHEMA UPDATE
------------------------------------

REPLACES the old 1:1 bot→context relationship:

datasets (was effectively "contexts" before, now standalone)
  id, client_id, name, type (crawl/upload/manual/database),
  source_url, crawl_status, chunk_count, created_at, updated_at

bot_datasets (NEW — the many-to-many join table)
  id, bot_id, dataset_id, linked_at

chunks, qa_pairs, data_sources — now reference dataset_id
  instead of bot_id or context_id directly
  (a chunk belongs to a Dataset, not to a Bot — the Bot just
  pulls from whichever Datasets are linked to it)

bots table stays as before:
  id, client_id, name, purpose, status, tone, created_at, updated_at
  (no longer holds knowledge directly — it's just config + channels
  + which datasets are linked via bot_datasets)

------------------------------------
HOW THE CHAT QUERY CHANGES (/api/chat)
------------------------------------
OLD: vector search ran against chunks WHERE context_id = X
NEW: vector search runs against chunks WHERE dataset_id IN
     (SELECT dataset_id FROM bot_datasets WHERE bot_id = X)

This is the only backend logic change — everything else (Q&A
pairs check, query cache, Groq generation) stays exactly the same,
just the WHERE clause now spans multiple datasets per bot.

------------------------------------
UPDATED QUICK REFERENCE — FEATURE → LOCATION
------------------------------------

Upload a PDF (as a dataset)            → Client Detail → Datasets tab → "+ New Dataset"
Assign datasets to a bot               → Bot Detail → Datasets tab → "Link existing dataset"
See which bots use a dataset           → Client Detail → Datasets tab → dataset card "used by" tag
Create a bot and pick its data         → Client Detail → Bots tab → "+ New Bot" wizard Step 3

WHATSAPP + EMAIL CHANNEL — SYSTEM DESIGN
===========================================
Goal: reuse the existing RAG brain, just add two new "ears and mouths"
(WhatsApp + Email) that feed into the same chat pipeline you already built.

-------------------------------------------------
HOW IT WORKS — END TO END
-------------------------------------------------

STEP 1 — Client connects their channel (in your dashboard)
  - Client goes to Settings → Channels
  - Enters WhatsApp Business number + connects via Meta API (OAuth/token)
  - Enters business email (connects via SMTP/IMAP or a provider like
    Resend/Postmark for sending, and a webhook for receiving)
  - This links their WhatsApp number / email address to their existing
    context_id — the same knowledge base they already built on the website

STEP 2 — Customer messages the business
  - WhatsApp: customer sends "hi I like that VXL 45, what's its cost and
    warranty?" to the client's WhatsApp number
  - Email: customer emails the client's support address with the same question

STEP 3 — Message lands on your server
  - WhatsApp: Meta sends the message to YOUR webhook endpoint
    (POST /api/channels/whatsapp/webhook)
  - Email: your email provider forwards the incoming email to YOUR
    webhook endpoint (POST /api/channels/email/webhook)
  - Both webhooks extract: sender (phone number or email), message text,
    and which client/context_id this belongs to (matched by the
    business number/email that received it)

STEP 4 — Same RAG pipeline you already built runs
  - Message text goes into your EXISTING /api/chat logic:
    Q&A pairs check → query cache check → vector search → Groq LLM
  - No new AI logic needed — this is the same brain, new doorway

STEP 5 — Reply sent back through the same channel
  - WhatsApp: your server calls Meta's Send Message API with the answer
  - Email: your server calls your email provider's Send API with the
    answer as a reply in the same thread
  - Message + response both logged to your existing "messages" table,
    tagged with channel = 'whatsapp' or 'email' (this also feeds your
    Inbox and Analytics automatically since they already read that table)

STEP 6 — Conversation continues naturally
  - Customer says "no thanks" → bot replies politely and conversation
    session just goes idle (WhatsApp: 24hr window closes / Email: thread ends)
  - If customer had asked for an order status, the order-lookup flow you
    already built (Google Sheets / REST API / CSV lookup) triggers exactly
    the same way it does on the website widget

-------------------------------------------------
WHAT'S ACTUALLY NEW (vs what you reuse)
-------------------------------------------------
REUSED AS-IS:
  - /api/chat pipeline (Q&A, cache, RAG, Groq)
  - Vector search, embeddings, chunking
  - Order database lookup logic
  - messages table + Inbox/Analytics (just add channel tagging)

NEW PIECES NEEDED:
  - WhatsApp webhook receiver + sender (channel adapter)
  - Email webhook receiver + sender (channel adapter)
  - A "channel router" — maps incoming phone number/email to the
    correct client's context_id
  - Message formatting layer — WhatsApp has character/media rules,
    email needs subject lines + HTML formatting, website widget doesn't
  - Session/thread tracking per channel (WhatsApp uses 24hr windows,
    email uses thread IDs, different rules than your sessionStorage)
